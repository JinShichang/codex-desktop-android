## PRoot seccomp 自动选择

安装准备、桌面会话和普通 Python 工具入口会先执行一个固定的嵌套启动测试。只有 PRoot 实际报告已启用 seccomp 加速，且多次 exec 与子进程测试正常退出时，才保留加速。若失败或未检测到加速，再验证关闭加速的兼容模式；兼容模式通过后才设置 `PROOT_NO_SECCOMP=1`。两种模式都失败时终止原操作，不执行安装脚本或用户任务，也不把设备永久标记为“不支持”。

结果保存在应用私有目录 `files/.proot-compat/`，按系统指纹、内核、APK 原生库位置及文件元数据、实际 rootfs 路径区分。更换系统、APK 原生库或运行环境会重新探测。缓存只保存模式与原因，不保存账号或会话；不扫描或校验整个环境包。普通 Python 工具与 Java 应用进程分开探测，避免直接复用不同执行入口的结果。

这里关闭的仅是 PRoot 的 seccomp 加速，不会关闭 Android 的 seccomp 安全策略。受保护 GNU 执行器原有的 `PROOT_NO_SECCOMP=1` 涉及路径转换与权限过滤顺序，继续保留。主机测试覆盖自动选择、兼容回退、缓存失效、超时和 Python `-I` 入口；具体 Android 机型的加速可用性与性能仍需实机验证。

## 设备验收

### v76 至 v80 本地测试版

桌面客户端升级为 `26.1117.31558`，GNU 后端升级为 `0.171.0`；包含 Android openat 路径兼容修复和手机操控上游更新。用户已反馈修复包、启动页调整及 v79 最近列表持续加载修复测试无异常。该反馈不等于所有高权限通道、ROM 或首次安装路径均已验收。

v80 将 APK 与完整环境分开。此前 v80 本地构建的小 APK 为 63,249,080 字节，配套环境包为 1,367,052,023 字节；该构建的 1432 项自动化测试、生产 Java 解包器实包提取、3988 项不可变启动清单验证、ARM64 QEMU 依赖检查及 APK 签名与对齐检查通过。上述检查在主机执行；v80 的 Android 首次安装、所有文件访问授权和 Download 自动检测完整流程仍待真机验证。 [安装说明](split-release.md)

源码最终检查另发现并修复首次拆分安装显式使用 `/usr/lib/chatgpt` 时被启动配置探测拒绝的问题：仅增加该精确内置路径，保留版本化目录白名单和非法路径拒绝。该修复附带首次安装路径及路径别名/穿越拒绝回归测试；上述已有 APK 未包含此修复，需重新编译后再用于首次安装验收。

### v71 本地测试版：配置共享、图形与日志

Android 工具页可选择以下图形模式，默认自动，下次启动桌面生效：

- 自动：检查 KGSL 接口和自带库，执行限时 GLX 像素及着色器探测；成功才选择 Zink/Turnip，失败转为 Debian Mesa llvmpipe。
- 兼容：移除自带 Vulkan ICD/库路径强制选择，使用 Debian Mesa llvmpipe。CPU 渲染可能增加功耗并降低流畅度。
- 加速：明确要求自带 Zink/Turnip，探测失败会报错并提示改用兼容模式。

启动就绪同时使用文件事件与轮询，标记必须匹配本次启动 token。不是仅凭文件存在认定就绪。

在 Android 工具页点击“导出日志到 /sdcard/codex/log”，生成独立 ZIP。写共享目录需要用户已授予所有文件访问权限。
归档包括 runtime.log、最近启动异常、已知输入法/窗口管理器/文件选择器/图形探测日志、当前应用 UID 的有限 Logcat 和设备/版本信息。
每个文件最多导出末尾 2 MiB；不收集 config.toml、auth.json、钥匙串、会话或数据库。已知密钥模式会脱敏，分享前仍请检查内容。

Codex 在系统文件选择器中提供“Codex → .codex”，由独立 CC Switch 选择整个目录并保存持久读写授权，无需 Root 或 PRoot 内安装 CC Switch。
首次启动并初始化 `.codex` 后才显示目录。内容原子替换不会改变逻辑文档 ID；重建运行环境或清除数据后需要重新授权。
目录中的普通文件和子目录可以浏览、读写与创建；支持删除普通文件及空目录。不会展开符号链接，也不提供授权根的删除操作。
写入先暂存，可靠关闭后提交，后续读取等待提交完成。文件发生可观察的外部修改时拒绝覆盖。
这不是对 guest 全部写入者的全局文件锁；切换前应安全退出桌面客户端，保存后重新启动并建立新会话。
CC Switch 首版仅修改 config.toml，保留 auth.json 和实际钥匙串；文件读回一致不等于正在运行的 Codex 已切换。

实机需要验证：

1. 三种图形模式的冷启动、界面完整性及重新选择；其他厂商 GPU 的软件回退。
2. 导出 ZIP 能在共享存储找到、解压，并保留实际失败原因。
3. CC Switch 连接 Codex 目录，授权在双方应用和手机重启后有效；撤销后明确报错。
4. config.toml 的创建、长内容换短内容、读回和备份恢复；MCP、工作目录及其他字段保留。
5. 重新启动 Codex 后使用新服务商和模型，官方登录及钥匙串不丢失。

以下为通用设备验收：

1. 记录应用版本、桌面版本、后端版本和 Android ROM。覆盖升级前核对签名并保留原有项目、登录和运行环境。
2. 验证冷启动、登录回调、中文输入、竖横屏、键盘遮挡和显式退出。Android 的子进程额度由系统共享，需在实际使用条件下观察后台恢复。
3. 以测试项目检查消息回复、本地命令输出、文件写入和两个独立会话。共享目录工作区应使用实际已授权的路径。
4. 分别检查前台 MCP 的读屏和输入、用户接管与停止。将可选的 Root 后台屏和其他高权限通道单独验收。
